# Manual outside acceptance

Run **Manual outside edge acceptance** with `workflow_dispatch` in the extracted website repository. It targets `https://openplans.openhra.com`. This workflow has no schedule and uses read-only checkout permissions. It needs no configured secret. If `OPENHRA_ALERT_SECRET` exists, the final job sends one summary through `tools/alerts/send.py`.

The preparation job runs the local fake-server tests and sets a rendezvous four minutes ahead. Linux and macOS jobs each open four MCP calls in four synchronized rounds, six seconds apart. Each source uses the edge's four-connection allowance, giving eight calls across the pair against the application's four-call limit. Each call uses `search` with `entity=plan`, Harris County (`48201`), year 2026 and a unique synthetic query containing the source, run ID, round and sample. Plan discovery reads the scoped catalog before filtering the query. Distinct queries bypass the generation-keyed response cache, including across repeated runs. The result limit stays at one; the test needs DB work, not large responses. The jobs assume separate hosted runner pools have distinct outbound addresses. They do not look up, log or retain those addresses. A late runner fails the check. The final job requires both reports and an application concurrency error with `Retry-After`. Every concurrency sample must be a valid successful tool stream or that application error. An edge-generated 429, application rate-limit 429, 502 or 504 fails the sample and does not count as application concurrency evidence.

Rerun all jobs after a failure. A failed-job-only rerun reuses the preparation job's expired rendezvous and the successful partner's old report. It cannot pass the paired concurrency check. Both sources must sample together against a fresh rendezvous.

Failed HTTP samples report the round, sample, status, fixed error classification and elapsed milliseconds. Response bodies and remote error messages stay out of the report. See the [macOS concurrency investigation](macos-concurrency.md) for the original 502 and the limits of its reproduction.

Each runner then checks the native catalog, modern metadata discovery/list/call, legacy initialize/list/call, JSON, incremental progress SSE, mid-stream client disconnect, exact CORS policy, method and body limits, protected routes, hostile Host and SNI, and forged forwarding headers. Modern revision `2026-07-28` uses `server/discover` with `_meta` protocolVersion, clientInfo and clientCapabilities keys under `io.modelcontextprotocol/`. It has no legacy initialize exchange. Revision `2025-11-25` uses initialize and the initialized notification before list/call. Legacy responses may use JSON or request-scoped SSE. Either form must contain exactly one successful result with the expected RPC ID. The modern ordinary-call check still requires JSON.

Regular MCP checks are paced to avoid consuming the burst allowance. Rate tests run last. Three workers send 16 ordinary requests, then three requests with rotated forged forwarding headers. This can exceed the edge's one-request-per-second rate plus ten-request burst without hitting its four-connection limit. Serial TLS handshakes on distant clients can refill the bucket before exhausting it. Both the ordinary burst and the forged burst must observe 429 with bounded `Retry-After`; application concurrency errors do not count. A normal refill may admit a call. If latency prevents saturation within these 19 requests, both checks fail. The client never tries real source-address rotation. The router's isolated adapter tests also prove that nginx overwrites the forwarded values with its socket peer.

The stream request advertises gzip support and requires an uncompressed response with `X-Accel-Buffering: no`. A stream passes only when a matching progress event arrives at least 25 ms before the final tool result in separate reads. The timing and disconnect checks read Harris County's 2026 plan catalog with different small result limits for each runner and check. A cold plan read does more work than an empty synthetic provider-name search, which can finish before the first packet reaches the client. A fast response or cache hit with no measurable gap still fails. Disconnect closes the socket after progress and before any final event in that read. The result reports the client action. An operator must confirm SQL cancellation and retained-log privacy on the host after the outside run. This client has no host access and creates no SQL lock to prolong calls. If ordinary synthetic reads finish too quickly to expose concurrency, the final table prints FAIL. Do not treat an unobserved limit as a pass.

The allowed-Origin POST check is tracked as the MCP3b known failure. Missing `Access-Control-Allow-Origin`, exposed headers or `Vary: Origin` still prints FAIL and fails the workflow. There is no skip, allowed-failure flag or automatic waiver. Deploy the application fix and rerun the matrix.

Every runner has a hard cap of 80 target requests, including TLS refusal attempts, and a ten-minute job timeout. Four rounds use 16 requests and the remaining checks use 62, for 78 per runner and 156 per complete matrix, plus one optional signed report. Six four-call rounds would exceed the cap, so this probe uses four rounds. Sockets have ten-second deadlines. MCP and ordinary response bodies are capped at 256 KiB. The native 50-plan catalog page has a separate 8 MiB cap because it includes source evidence; the first live triage measured 6,255,669 bytes. Bodies are never printed or saved. Requests use synthetic search markers and public catalog filters only. There are no household estimates, real bearer credentials, arbitrary target inputs, redirects or retries.

Run offline tests from the website root:

```sh
python3 -B -m unittest discover -s tests -p 'edge_acceptance*.py'
```

The paired concurrency fake returns immediate successful streams with no overlapping application work, and the aggregate check must FAIL because no application refusal was observed. With slow overlapping calls and the same four-call application limit, it must PASS. Both cases require all 16 samples across two test rounds and distinct plan queries. The fakes also test both protocol envelopes, including legacy SSE. Wrong IDs, RPC errors, missing or duplicate results, incomplete streams, oversized catalog pages, buffered SSE, successful GET, oversized-body acceptance, accessible private routes, a successful hostile Host, missing CORS headers, missing Retry-After and forwarding-based rate evasion must fail. A one-request-per-second leaky-bucket fake with connection latency reproduces the serial-burst blind spot and accepts the corrected probe. TLS refusal tests ensure certificate hostname errors cannot masquerade as refused SNI. These tests run in the preparation job and in `tools/gate.sh`, including the full gate.

A passing workflow provides outside-client evidence. Confirm SQL cancellation and retained-log privacy on the host before closing deployment acceptance.

## Host-side proof, 2026-11-08

The revised workload used 22 live requests, below the 40-request allowance. Two setup requests to the existing loopback app listener returned one Host-policy 403 and one valid catalog stream. Two synchronized four-call rounds from each logical source then made 16 requests directly to that listener. Eight returned valid successful tool streams and eight returned application concurrency 429 with bounded `Retry-After`. Every sample passed; no 502 or 504 occurred. The paired aggregate check passed.

One further four-call round through the public edge returned four valid successful streams and no refusals, as expected for a single source using four slots. This host-side proof does not reproduce the hosted runners' distinct outbound sources. The full two-runner outside workflow remains to be run after publication. No workflow was dispatched and no deployment was changed.
